# HW3. Нормальные формы

## Текущие таблицы

В проекте BookStore DB сейчас есть такие таблицы:

- authors
- categories
- customers
- books
- orders
- order_items

После просмотра схемы видно, что она уже в основном нормально разделена на сущности. Явных нарушений 3НФ и НФБК в текущей схеме нет.

Ниже показаны два простых примера, как таблицы могли бы выглядеть до нормализации и какие проблемы из-за этого могли бы появиться.

## Пример 1. Books до нормализации

Плохой вариант таблицы:

```text
Book(
    id,
    title,
    price,
    author_id,
    author_name,
    category_id,
    category_name
)
```

Зависимости:

```text
id -> данные книги
author_id -> author_name
category_id -> category_name
```

Получаются транзитивные зависимости:

```text
id -> author_id -> author_name
id -> category_id -> category_name
```

Из-за этого таблица не соответствует 3НФ, потому что данные автора и категории зависят не напрямую от книги, а от других полей.

Аномалии:

- Аномалия обновления: если у автора несколько книг, его имя хранится несколько раз. При изменении имени нужно изменять несколько строк.
- Аномалия вставки: нельзя нормально добавить автора, пока у него нет книги.
- Аномалия удаления: если удалить последнюю книгу автора, можно потерять информацию об авторе.

Решение:

Данные нужно вынести в отдельные таблицы:

- authors
- categories
- books

В таблице books остаются author_id и category_id как внешние ключи.

## Пример 2. Orders до нормализации

Плохой вариант таблицы:

```text
Order(
    id,
    order_date,
    status,
    customer_id,
    customer_name,
    customer_email
)
```

Зависимости:

```text
id -> данные заказа
customer_id -> customer_name, customer_email
```

Получаются транзитивные зависимости:

```text
id -> customer_id -> customer_name
id -> customer_id -> customer_email
```

Это тоже нарушение 3НФ, потому что данные клиента хранятся внутри заказа, хотя относятся к отдельной сущности.

Аномалии:

1. При изменении email клиента его пришлось бы менять во всех заказах.
2. Нельзя добавить клиента, пока у него нет заказа.
3. При удалении последнего заказа можно потерять информацию о клиенте.

Решение:

Нужно разделить данные на таблицы:

- customers
- orders

В orders оставить только customer_id.

## Вторая нормальная форма

Почти во всех таблицах используется простой первичный ключ id, поэтому проблема частичной зависимости там не возникает.

Отдельно можно посмотреть таблицу order_items:

```text
order_items(
    order_id,
    book_id,
    quantity,
    price
)
```

Первичный ключ:

```text
(order_id, book_id)
```

Зависимость:

```text
(order_id, book_id) -> quantity, price
```

quantity и price относятся к конкретной книге в конкретном заказе, поэтому зависят от полного составного ключа. Следовательно, таблица order_items находится во 2НФ.

## Третья нормальная форма

Основные зависимости в текущей схеме:

```text
authors:
id -> first_name, last_name, country, birth_year

categories:
id -> name, description

customers:
id -> first_name, last_name, email, phone, registration_date, address

books:
id -> title, price, stock_quantity, description, author_id, category_id, isbn

orders:
id -> order_date, status, total_amount, customer_id

order_items:
(order_id, book_id) -> quantity, price
```

После разделения сущностей данные автора, категории и клиента не дублируются в книгах и заказах. Неключевые поля зависят от ключей своих таблиц. Поэтому таблицы находятся в 3НФ.

## Нормальная форма Бойса-Кодда

Для НФБК левая часть каждой значимой функциональной зависимости должна быть ключом или суперключом.

Проверка таблиц:

```text
authors:
id -> остальные поля
id является первичным ключом.

categories:
id -> остальные поля
id является первичным ключом.

customers:
id -> остальные поля
id является первичным ключом.

books:
id -> остальные поля
id является первичным ключом.
isbn имеет UNIQUE, поэтому тоже может выступать потенциальным ключом.

orders:
id -> остальные поля
id является первичным ключом.

order_items:
(order_id, book_id) -> quantity, price
Пара (order_id, book_id) является первичным ключом.
```

Для рассматриваемых зависимостей таблицы соответствуют НФБК.

## Примечание про orders.total_amount

Поле total_amount можно вычислять по позициям заказа из order_items. Само наличие этого поля не означает автоматически нарушение 3НФ, но может вызвать проблему согласованности данных: например, позиции заказа поменяли, а total_amount забыли обновить.

## Итог

После нормализации база состоит из:

- authors
- categories
- customers
- books
- orders
- order_items

Нормализация позволила избежать:

- дублирования данных;
- аномалий вставки;
- аномалий обновления;
- аномалий удаления.

Текущая схема удовлетворяет 3НФ и НФБК.
